============================================================================
SMART HOSE LEAK DETECTION SYSTEM - OPERATOR GUIDE
============================================================================
Keep this open when you are setting up. Everything you need to run the
system, connect the ESP32, and fix the things that usually go wrong.

Last updated: 28 October 2026 (admin role + multi-barangay console)


============================================================================
0. THE 60-SECOND VERSION
============================================================================
1. Open a terminal in D:\USB Drive\SmartHoseLeak
2. Run:   .venv\Scripts\activate
3. Run:   python manage.py runserver 0.0.0.0:8000
4. Read the two addresses it prints. Open the "On the network" one.
5. Log in as  facilitator / facilitator123
6. Power the ESP32. Within ~10 seconds the dashboard should say Online.

If it says Offline, go to section 7.


============================================================================
1. HOW THE PIECES FIT TOGETHER
============================================================================
  ESP32  --(WiFi, every 2s)-->  Django server on your laptop  -->  Dashboard
                                       (the database)              (browser)

  - The ESP32 PUSHES readings. The server never asks for them.
  - "Online" is not detected. It just means a reading arrived in the last
    10 seconds. A powered board with the wrong server address looks exactly
    the same as an unplugged board.
  - The leak decision and the SMS happen ON THE BOARD. They keep working
    even with the server off, the WiFi down, or no internet at all.
  - The server owns history, households, complaints and notifications.

Two things are both called "the dashboard". Do not mix them up:
  - Django dashboard   http://<laptop-ip>:8000/dashboard/   (the real system)
  - The ESP32's own page   http://<device-ip>/              (live values only)


============================================================================
2. STARTING THE SYSTEM
============================================================================
Open Command Prompt in the project folder, then:

    .venv\Scripts\activate
    python manage.py runserver 0.0.0.0:8000

IMPORTANT: the "0.0.0.0:8000" part is not optional.
Plain "python manage.py runserver" listens on this computer ONLY. The ESP32
cannot reach it, your phone cannot reach it, and the dashboard will sit at
Offline forever. The command warns you if you forget.

It prints something like:

    Addresses for this session
      On this computer   http://127.0.0.1:8000/dashboard/
      On the network     http://172.20.10.2:8000/dashboard/

      ESP32 Server address (paste into the device's /wifi page):
          http://172.20.10.2:8000/api/ingest/

Use the "On the network" address in your browser. Copy the last line into
the ESP32 when the network changes (section 5).

Windows Firewall may ask for permission the first time. Click ALLOW.
To stop the server: press Ctrl+C in that terminal window.

3. LOGINS
============================================================================
  Administrator (admin console)     admin / <shown once by setup_demo>
  Facilitator (full dashboard)      facilitator / facilitator123
  Household owner (owner portal)    hh001 / demo12345

  ESP32 settings page (/wifi)       admin / leakadmin
  ESP32 setup hotspot               LeakDetect-Setup / leakdetect123

THREE ROLES NOW, NOT TWO. setup_demo creates a separate "admin" login as
well as the facilitator:

  - Admin signs in and lands on the ADMIN CONSOLE at /console/. From there
    they manage everything: facilitator accounts, household registration,
    visit scheduling, every login in the system (suspend or delete),
    announcements, analytics, data/backups, the audit log and maintenance.
  - Sidebar -> Administration -> Households (/console/households/) is the
    admin's register of households: a searchable list of everyone added,
    with Edit and Delete on each row (both open as dialogs on the page),
    and a "Register household" button that opens the registration dialog.
    The admin enters the household in words only: owner, purok/street
    (province, municipality and barangay are shown read-only - one barangay
    is served), contact, email, notes. A hose line AND a new board are
    registered with it automatically. It then shows "Pending activation" until
    the facilitator activates it - adds the coordinates and creates the
    owner's login (section 3e). The list shows who activated it and when.
    Adding a facilitator works the same way on the Facilitators page
    (/console/facilitators/): every facilitator is numbered FAC-001,
    FAC-002 ... automatically on creation (never typed, never editable),
    shown in the first column; Edit changes name/contact/email only (the
    login, password and number stay), Delete removes the account - visits
    assigned to that person stay on the schedule as Unassigned.
    Deleting a household also removes its complaints, notices and the
    owner's login; the hose line and its readings stay. Every add, edit and
    delete is written to the audit log.
  - EVERY ADD/EDIT FORM OPENS AS A DIALOG on the page it belongs to, for
    all roles: register household / add facilitator / schedule a visit /
    new announcement / edit a visit (on the visit's page) / edit a login's
    contact details (Accounts), and on the facilitator side add/edit a
    household (list and record pages) or a hose line. The Overview buttons
    land on the right page with the dialog already open (?open=...).
    Without JavaScript each button is still a plain link to a full-page
    version of the same form.
    Admin and facilitator are SEPARATE roles: an admin sees only the
    console, not the facilitator dashboard.
  - THE SYSTEM SERVES ONE BARANGAY (Lower Dakong Patag). Nothing asks which
    barangay anything belongs to; records are attached to it automatically.
    (The data model can hold more than one - that is simply switched off in
    the screens.)
  - A facilitator lands on the monitoring dashboard at /dashboard/ and works
    inside their own barangay only. They CANNOT open the console.
  - Neither role can open the other's pages; each is turned away with a 403.
  - Any Django superuser is treated as an admin. The demo facilitator is not
    a superuser, so it exercises the plain facilitator role.

  setup_demo prints the admin password once when it first creates the
  account. To set a known one:  python manage.py setup_demo --password <pw>
  (that password is used for BOTH the admin and the facilitator on first
  creation). A forgotten admin password is reset with createsuperuser or
  "python manage.py changepassword admin".

Households hh002-hh006 have generated passwords that cannot be recovered.
To give an owner a new one: log in as facilitator, open the household, and
use the reset-password button on their record.

CHANGE "leakadmin" AND "leakdetect123" BEFORE THE DEFENCE. They are the
shipped defaults and are written in the firmware source.

3b. VISIT SCHEDULING
============================================================================
The admin schedules household visits; the facilitator carries them out.

ADMIN  (console sidebar -> Visits -> Visit schedule -> "Schedule a visit")
  Pick the household (it needs NO portal account yet - the text goes to the
  number on its record), give the visit a title, choose the FACILITATOR and
  the DATE. Saving with a facilitator chosen schedules it and TEXTS both the
  household and the facilitator. Saved without a facilitator it waits as
  "Requested" until one is assigned from the visit's page.
  The console Overview shows the next visits; "All visits" lists them with a
  status filter.

FACILITATOR  (sidebar -> Schedule)
  Who they will visit and when, grouped by day: Overdue, Today, Tomorrow,
  Later this week, Later, Not yet scheduled. "Start" and "Mark done" with a
  note. The dashboard carries a "Your schedule" card with the next three,
  and each visit has a NAVIGATE link (section 3f).

THE SMS
  Uses the same SMS queue as everything else (section 9c). With no
  credit or no API key the texts wait in the queue and go out later - the
  visit is scheduled either way. So "scheduled but nobody got a text yet" is
  usually the SMS queue, not a fault here.


============================================================================
3c. ANNOUNCEMENTS & ANALYTICS (admin console)
============================================================================
ANNOUNCEMENTS  (console sidebar -> Communications -> Announcements)
  The admin's version of the facilitator's "Notices & SMS", but able to reach
  more than one barangay. Pick an audience - every active household, one
  barangay, or specific households - a title and a message, and the channels
  (in the app, by SMS, or both). It is delivered the same way a facilitator
  notice is: it shows up in each household's Notices feed, and SMS goes
  through the same SMS queue (section 9c). The list is a history with
  the reach of each one.

PRESSURE & FLOW  (console sidebar -> Administration -> Pressure & flow)
  The admin's read-only view of live pressure and flow for EVERY household,
  across every barangay - the same tiles, table and history chart the
  facilitator monitors, widened to the whole system. Export pressure log
  (CSV) gives the last 24h of minute rollups. The facilitator acts on these;
  the admin oversees them.

ANALYTICS  (console sidebar -> Administration -> Analytics)
  Headline totals plus simple bar charts across every barangay: households
  and leak alerts per barangay, work orders by status and kind, complaints by
  status, and SMS delivery. Leaks and SMS cover the last 30 days. The charts
  are drawn in the page itself (no chart library), so they need no internet
  and print cleanly for the defence.


============================================================================
3d. DATA & SYSTEM OPS (admin console)
============================================================================
DATA & BACKUPS  (console sidebar -> System -> Data & backups)
  - Export: households, work orders and the audit log as CSV, across every
    barangay, for the LGU's records.
  - Import households: upload a CSV with a header row of owner_name, address,
    contact_number and optionally barangay. Rows that name no barangay use
    the one you pick on the page; a row with no owner_name is skipped.
  - Backup: downloads a full JSON copy of the data. It contains sensitive
    details (logins, device keys) - keep the file somewhere safe.
  - Restore: upload a backup JSON. It OVERWRITES records that share an id with
    the backup and adds any it is missing; it does NOT delete newer rows. You
    must type RESTORE to confirm. Built on Django's dumpdata/loaddata.

AUDIT LOG  (console sidebar -> System -> Audit log)
  Who did what, and when: account suspensions and deletions, facilitator
  creation, work-order approvals and rejections, announcements, backups,
  restores and maintenance toggles. Write-once - there is no edit or delete.

SYSTEM STATUS  (console sidebar -> System -> System status)
  - Maintenance mode: turn it on to show households and facilitators a short
    notice and keep them out while you work. The ADMIN CONSOLE and the DEVICE
    INGEST stay live on purpose - you can still turn it off, and the boards
    never stop recording water. Turn it off to let everyone back in.
  - Recent errors: the last server errors, newest first, so a 500 leaves a
    trace you can see here instead of only in the terminal. The full traceback
    stays in the server log.

3e. THE FACILITATOR SIDE  (one barangay each)
============================================================================
A FACILITATOR SEES ONLY THEIR OWN BARANGAY. Every facilitator screen -
dashboard, households, lines, pressure, alerts, complaints, notices & SMS,
reports and exports, and the live map feed - shows only the barangay the
admin assigned to their account. A link into another barangay's record
simply comes back "not found". A facilitator with NO barangay assigned sees
an empty dashboard with a notice saying so; the admin assigns one at
Console -> Facilitators / Accounts.

  - Each barangay has its OWN main water source (Lines page, top). The
    facilitator places theirs; the map draws that barangay's hoses from it.
  - Leak-alert texts go to the facilitator OF THAT LINE'S BARANGAY, not to
    every facilitator in the system.

EVERYTHING THE FACILITATOR COULD DO BEFORE STILL WORKS (households, lines,
boards, alerts, complaints, notices, reports). New on top of it:

TEXTING A HOUSEHOLD ITS LOGIN
  REGISTERING A HOUSEHOLD IS A TWO-PERSON JOB.
    1. The ADMIN enters the household during application (console ->
       Households -> Register household): owner, purok/street, contact,
       email, notes. The hose line and a new board are created at once.
       No location, no login: the record shows "Pending activation".
    2. The FACILITATOR opens Households (the dashboard's "Activate
       households" button lists the pending ones; the search box finds a
       name, ID, address or number), clicks ACTIVATE on the household, sees
       what the admin entered read-only, types the LATITUDE and LONGITUDE
       of the house, and clicks Create account. That creates the Owner
       Portal login: the username and temporary password are shown once
       and sent to the household by text and, if it has an email, by
       email. The owner is asked to change the password on first sign-in.
       ACTIVATION NEEDS A BOARD on the household's line (the row says
       "Register board" until there is one): the board's setup code is
       issued at the same moment and sent to the owner as a second text /
       email. The OWNER connects the board to their own WiFi - section 9d.
    The admin's list shows who activated each household and when. The
    facilitator can still Edit a household (including its coordinates) and
    reset or re-send a password from the household's record.

SCHEDULE  (sidebar -> Schedule)
  Who you will visit and when, grouped by day: Overdue, Today, Tomorrow,
  Later this week, Later, Not yet scheduled. "Start" and "Mark done" with a
  note. The dashboard carries a "Your schedule" card with the next three.

NOTICES BY EMAIL
  Notices & SMS has a third tick, "Also send by email", for households with
  an email on their record (or on their login). Needs the mailbox in
  section 3g; without it the email is printed to the server terminal.


============================================================================
3f. VISIT ROUTES ON THE MAP, AND NAVIGATE
============================================================================
TWO KINDS OF LINE ON THE LEAK MAP
  - SOLID line  = the hose. It runs cross-country from the source and is
                  drawn STRAIGHT on purpose: it means "this house is on this
                  hose", not "this is the path of the pipe".
  - DOTTED line = the VISIT ROUTE: the road from the barangay's water source
                  to the house, for a facilitator going out there. Tick
                  "Visit routes" above the map to show or hide them.

WHERE ROUTES COME FROM
  Fetched ONCE from OpenRouteService (a free routing service) when a
  household's coordinates are saved - or when the barangay's water source is
  moved - and stored on the household. The map then draws them with no
  internet and no further calls, exactly like the hoses.

SETTING IT UP  (once)
  1. Sign up free at openrouteservice.org and copy your API key.
  2. Put it in .env:
         ORS_API_KEY=your-key-here
  3. Restart the server.
  4. For households surveyed BEFORE the key existed:
         python manage.py fetch_routes          (only the ones without a route)
         python manage.py fetch_routes --all    (redo every one)
  Without a key nothing is fetched and the map simply shows no routes; the
  hoses and everything else are unaffected. The household record says why
  ("No OpenRouteService key set").

ON THE HOUSEHOLD RECORD  ("Getting there")
  The route's length and time by road, a "Fetch route / Refetch route"
  button for when the first attempt failed, and NAVIGATE.

NAVIGATE  (household record, Schedule cards, admin work order, map pins)
  Opens Google Maps directions on the phone, from the water source to the
  house - real turn-by-turn, in the app people already have. Needs no key.
  This is the thing that actually gets someone to the door; the dotted route
  is the overview.

A CAVEAT ABOUT RURAL ROADS
  OpenStreetMap's road data around Sison is thin in places. A house on a
  footpath the map does not know about routes to the nearest known road and
  ends in a short straight stub. That is the map data, not a fault - use
  Navigate for the last stretch. ROUTING_PROFILE=foot-walking in .env makes
  the service use footpaths where it has them.

3g. SIGN-IN CODES (OTP), EMAIL, AND THE APP ON EVERY PHONE
============================================================================
SIGNING IN NOW HAS TWO STEPS, FOR EVERY ROLE
  1. EMAIL OR USERNAME, plus password. Either identifier works: households
     built on short usernames (hh002) still use those; anyone with an email
     on their account can type that instead. (Email only resolves when one
     account carries it; it is not forced to be unique on the table.) On the
     sign-in dialog, pick where the code should go - Text or Email - and
     optionally "Remember this device for 30 days".
  2. A 6-DIGIT CODE arrives by text (iprogSMS) or email. Type it in. It is
     good for 10 MINUTES and 5 wrong guesses; "Send a new code" is allowed
     once a minute and can switch channel.

  FORGOT A PASSWORD: the "Forgot your password?" link on the sign-in dialog
  emails a one-time reset link to the address on the account. The link is
  built from the host the page was opened on, so open it through the public
  tunnel (not 127.0.0.1) for a link that works off this machine. Accounts
  with no email on file cannot self-reset - a facilitator sets a new password
  from the household record (section above), or use Django admin.

  If the channel you picked is not on your account (no email, say), the
  other one is used and the code page says where it went. An account with
  NEITHER a number nor an email signs in on the password alone, with a
  warning - add one in the console (Accounts) or Django admin.

  REMEMBER THIS DEVICE sets a signed cookie on that browser for 30 days;
  signing out does not clear it (the device is trusted, not the session).
  Clearing the browser's cookies does.

  IN DEVELOPMENT (DEBUG=True) THE CODE IS ALSO SHOWN ON THE SIGN-IN PAGE,
  so a demo never depends on SMS credit or a mailbox. Never in production.
  To switch the step off entirely: OTP_ENABLED=False in .env.

EMAIL  (one-time setup, about 5 minutes)
  Sign-in codes by email, and "Also send by email" on notices and
  announcements, go out from the project mailbox smarthoseleak@gmail.com.
  It needs an APP PASSWORD, which is a 16-letter code Google issues for
  one program - not the Gmail password:

    1. Sign in to Gmail as smarthoseleak@gmail.com.
    2. Google Account -> Security -> turn on 2-Step Verification (required).
    3. Google Account -> Security -> 2-Step Verification -> App passwords
       (or search "App passwords" in the account settings). Name it
       "Smart Hose Leak", click Create, copy the 16 letters.
    4. In .env, paste it (spaces or not, both work):
          EMAIL_HOST_USER=smarthoseleak@gmail.com       (already there)
          EMAIL_HOST_PASSWORD=abcd efgh ijkl mnop
    5. Restart the server, then prove it:
          python manage.py send_email your.own@address.com
       It says "Sent" and the message arrives (check spam the first time).

  Admin console -> System status -> Services shows whether email, SMS and
  routes are set up, in one place. Until the app password is in, every
  email is PRINTED TO THE SERVER TERMINAL instead of sent, the pages say
  email is not set up, and a sign-in code by email that cannot be sent is
  reported as such (it is not claimed as sent).
  Households get an email address on their record (Add/Edit household);
  facilitators on their account (console -> Facilitators -> Add).

LANGUAGE: ENGLISH / FILIPINO
  A small EN/FIL switch sits in the top bar on every page. It stores the
  choice in a cookie (django_language) and is also honoured from the
  browser's language setting. Translated so far: the public landing page and
  the whole sign-in flow (login, the code step, and password reset). The rest
  of the app stays English; untranslated text simply shows in English.

  Strings are Django's gettext catalogs under locale/fil/. To change or add
  Filipino wording, edit locale/fil/LC_MESSAGES/django.po, then compile:
        python manage.py compilemessages -l fil
  After wrapping NEW text in a template ({% trans "..." %} or
  {% blocktrans %}...{% endblocktrans %}, with {% load i18n %} at the top),
  re-extract first:
        python manage.py makemessages -l fil --ignore=.venv --ignore=staticfiles
  Both need GNU gettext on PATH (msgfmt/xgettext; MinGW provides them here).
  Restart the server after compiling.

THE APP ON EVERY PHONE
  All three roles can install the app (the same one). On an https address
  the user menu (top right) shows "Install the app on this device" when
  the browser offers it; the public landing page has the install button for
  households. The installed icon opens straight into whichever portal the
  signed-in person belongs to. Section 12f has the https requirement and
  the iPhone steps.


============================================================================
4. CONNECTING THE ESP32 TO A NEW WIFI NETWORK
============================================================================
The WiFi name and password are NOT in the code. They live in the board's
own memory, so this needs a phone, not a laptop.

IF THE OLD NETWORK IS GONE (you moved location):
  1. Just power the board on and wait about 2-3 minutes.
     It tries the saved network, fails 5 times, and then raises its own
     hotspot automatically.
  2. On your phone, join the WiFi network:  LeakDetect-Setup
     Password:  leakdetect123
  3. A setup page should pop up by itself. If not, open a browser and go to
     http://192.168.4.1/
  4. Pick the new network from the list, type its password, press Save.
  5. The board reboots and joins. THE HOTSPOT DISAPPEARING MEANS IT WORKED.

IF THE BOARD IS STILL REACHABLE AND YOU WANT TO SWITCH NETWORKS:
  Open http://<device-ip>/wifi , log in with admin / leakadmin, choose the
  new network, Save. Or press "Forget saved network" to force setup mode.

IF THE NETWORK LIST IS EMPTY:
  Press "Rescan networks". If it is still empty, use the "Or type the
  network name" box - typing the name always works and skips the scan.


============================================================================
5. TELLING THE ESP32 WHERE THE SERVER IS
============================================================================
IN MOST CASES YOU NO LONGER HAVE TO. The board asks the network where the
server is and remembers the answer.

  - At boot, if it has never been told an address, it asks.
  - While running, if three uploads in a row fail to reach anything, it asks
    again - about six seconds - and adopts the new address if one replies.
    It will not ask more than once every 30 seconds.
  - Whatever it finds is saved, so it comes back up already pointed at the
    right place.

This is why the startup banner says "Devices can find this server by
themselves". It only works when the server is started with 0.0.0.0:8000;
bound to localhost there is nothing for a device to find.

Watch for this in the Serial Monitor:
    [DISCOVER] Server found at http://192.168.1.21:8000/api/ingest/
    [DISCOVER] No server answered on this network.

Set it by hand when the board is on a different network from the laptop, or
when you want it pointed somewhere specific:


This is separate from WiFi, and it is the #1 reason the dashboard stays
Offline after moving to a new place.

Your laptop's address CHANGES when it joins a different network. The board
must be told the new one. This does NOT need a reflash any more.

  1. Start the server (section 2) and read the "ESP32 Server address" line.
     Or open the Django dashboard - if no readings have arrived it shows a
     "Device setup" panel with the exact line to copy.
  2. On your phone or laptop, open   http://<device-ip>/wifi
     Log in with  admin / leakadmin
  3. Put the address in the "Server address" box, e.g.
         http://172.20.10.2:8000/api/ingest/
  4. Leave the WiFi fields BLANK and press Save.
     It saves without rebooting and the next upload uses it.

Notes:
  - It must start with http:// and end with /api/ingest/
  - Never use 127.0.0.1 or localhost. On the ESP32 those mean the ESP32
    itself. The page will refuse them.
  - The board remembers this address after a power cut.

6. FINDING YOUR LAPTOP'S IP ADDRESS
============================================================================
Easiest: it is printed when you start the server (section 2).

By hand:
    ipconfig

Look for the section "Wireless LAN adapter Wi-Fi:" and read its
IPv4 Address.

WATCH OUT: this laptop shows TWO addresses. The extra one (192.168.137.1)
belongs to a dormant Windows hotspot adapter and DOES NOT WORK.
The correct one is the one that has a "Default Gateway" listed under it.

From a phone with no laptop access: install Fing (free) and scan the
network - the laptop appears as LAPTOP-MAG82PTI with its IP. On an iPhone
hotspot the phone is always 172.20.10.1 and the laptop is usually
172.20.10.2.


============================================================================
7. WHEN THE DASHBOARD SAYS OFFLINE
============================================================================
Work down this list in order. Most of the time it is #1 or #2.

1. IS THE SERVER LISTENING ON THE NETWORK?
   Run:  netstat -ano | findstr :8000
   You want:  0.0.0.0:8000        LISTENING
   If it says 127.0.0.1:8000, stop the server and restart it with
   "0.0.0.0:8000" (section 2).

2. IS THE SERVER ADDRESS ON THE BOARD CORRECT?
   Compare the address in section 2 against what the board has. Open
   http://<device-ip>/status and look at "server_url".

3. ARE THEY ON THE SAME WIFI?
   The ESP32 and the laptop must be on the same network. A phone hotspot
   counts, as long as both joined it.

4. WHAT DOES THE SERIAL MONITOR SAY? (section 8)
   [UPLOAD] OK                 -> working, problem is elsewhere
   [UPLOAD] REJECTED 401       -> wrong API key
   [UPLOAD] Failed: ...        -> cannot reach the laptop; check 1-3
   [UPLOAD] Skipped - WiFi ... -> not on WiFi; see section 4

5. FIREWALL
   Windows Firewall may be blocking Python. Test from your PHONE: open
   http://<laptop-ip>:8000/ - if the login page loads, the network path is
   fine and the problem is on the board.


============================================================================
8. THE SERIAL MONITOR (Arduino IDE)
============================================================================
Plug the ESP32 into USB, then:
    Tools -> Serial Monitor      (or Ctrl+Shift+M)
    Set the baud rate to 115200  (bottom-right dropdown)
    Set Tools -> Port to the ESP32's COM port

Lines worth knowing:
    [WIFI] Connected. Dashboard: http://192.168.1.42/   <- the board's IP
    [WIFI] Scan result: 7 network(s)                    <- WiFi scan worked
    [UPLOAD] OK                                         <- server receiving
    [UPLOAD] REJECTED 401 ...                        <- key not recognised
    [ID] Claimed as esp32-01                         <- board has an identity
    [ID] Not claimed. Enter a claim code ...         <- it does not (sec 9d)
    [CLAIM] Success. This board is esp32-01.         <- claiming worked
    [CLAIM] could not reach the server ...           <- WiFi has no internet
    [VALVE] Sealed at 0.812 bar. Holding 300 s.      <- leak test running
    [FLOW] Ignoring 538.6 L/min ...                  <- noise on the flow wire
    [M1] P=2.41 bar ... valve=open | NORMAL (none/none)   <- live readings


============================================================================
9. SERIAL MONITOR COMMANDS  (115200 baud)
============================================================================
ZEROING - do this once per board, before trusting any reading.

    Z         zero the pressure sensor. EMPTY THE LINE FIRST.

  Until this is done the board reports its own resting voltage as pressure -
  about 0.45 bar on a dry hose. Every threshold is then compared against a
  number that means nothing, and an empty hose looks like a working one.

VALVE

    V         run a sealed-line test now. It still waits until the line has
              been idle for 10 minutes; cutting water off while somebody is
              using it is not something a demonstration gets to override.
    O         open the valve, abandoning any test in progress.
    N         pretend it is night, on or off - for testing the night-flow
              window without staying up until 1 AM.

SIMULATION - inject fake readings without water running:

    S1,1.2,4.5    pretend 1.2 bar and 4.5 L/min
    R1            back to the real sensor
    R             back to the real sensor

  Simulated readings are flagged in the dashboard, so they cannot be
  mistaken for real data.

THERE IS NO CALIBRATION ANY MORE.
  The C / A / F commands went with the Q = K x sqrt(P) method. It needed a
  field calibration nobody could do reliably, and only ever described a line
  whose conductance had not changed since the day it was measured. The four
  tests in section 9e replaced it and need no calibration at all.


============================================================================
9a. ONE HOSE LINE PER HOUSEHOLD
============================================================================
The system used to be three sensor pairs on one board, strung along a single
run, with a leak reported as "somewhere between 15 m and 30 m". It is now one
hose per household - main source straight to the house - with its own board.

============================================================================
9b. SETTING THE LOW-WATER-SUPPLY THRESHOLD  (from the dashboard, no reflash)
============================================================================
Each supply line has its own pressure threshold. Below it, that line is
reported as Low Water Supply. You change it in the browser and the board
picks it up on its next upload - within about 2 seconds. Nothing is flashed
and nothing is restarted.

TO CHANGE IT
  1. Dashboard -> Lines
  2. Click Edit on the line
  3. "Low supply below" - type the value in bar
  4. Save changes

The Lines table shows every line's current threshold, in bar and psi. The
board's own page (http://<esp32-ip>) shows it too, in the "Low below" column
right next to the live pressure, so you can see on site whether a LOW SUPPLY
reading is a weak line or a threshold set too high for it.

WHAT VALUE TO USE
Pressure and height are the same thing in a gravity system: 1 bar is about
10 metres of drop from the source tank down to the sensor. So the right
threshold is different for every line, and it depends on your site, not on
the code.

  under 0.2 bar    effectively no water
  0.2 - 0.3 bar    a trickle
  0.3 - 0.5 bar    usable but low
  0.5 - 2.0 bar    normal for a gravity-fed rural system
  over 4 bar       unusual for gravity - a pump, or a closed valve

The default is 0.3 bar, which is about 3 m of head - the minimum pressure
rural gravity systems are designed around. It is a safe starting point, not
an answer.

TO FIND THE REAL VALUE FOR A LINE
  1. Zero the sensors first (section 9, the Z command). Until that is done
     the pressure figures are the sensor's own resting voltage, not water,
     and any threshold is being compared against a meaningless number.
  2. Run the line normally for a full day - morning, midday, evening.
  3. Find the lowest pressure seen during a stretch when everybody agreed
     the water was fine.
  4. Set the threshold 20-30% below that.

That way "low supply" means "lower than this line has ever been while
working", which is the only definition that will not cry wolf.

NOTES
  - The form refuses 0 (could never trigger) and anything above 4 bar (would
    trigger forever on a gravity line).
  - The board keeps the last value it was told, in flash. If the WiFi drops
    or the board reboots, it carries on using your figure - not the default.
  - A board that has never reached a server uses 0.3 bar.

9c. SENDING SMS  (Notices & SMS tab)
============================================================================
WHAT SENDS IT
  Semaphore (iprogsms.com), a Philippine SMS gateway, over the internet.
  There is NO GSM module on the server any more.

  The earlier plan was a SIM800L plugged into this laptop. It was dropped
  because a hosted server has no USB port to plug a modem into, and the code
  can only open a port on the machine it is running on - so the modem and the
  server would have to stay in the same room forever. A gateway works from
  this laptop and from a hosted server alike, so nothing has to change later.

  What that gives up is SMS during an internet outage. The answer to that is
  the SIM800L on the BOARD, which texts the owner directly when it cannot
  reach the server at all. Different module, different job.

SETTING IT UP  (about 5 minutes)
  1. Sign up at iprogsms.com. They give trial credits.
  2. Copy your API key.
  3. Put it in .env in the project folder:

         IPROGSMS_API_TOKEN=your-key-here

  4. Restart the server. It prints:

         SMS: Texts are going out. Credit: 100.

  The same line is at the top of the Notices & SMS page, because running out
  of credit is the failure that looks most like the system being broken, so
  it is shown before you write anything. It says one of:

         Texts are going out. Credit: 100.        nothing to do
         Texts are going out, but credit is low - 12 left.   top up soon
         There is no SMS credit left, so no text can be sent.    AMBER

  The last one is a stop, not a warning: at zero credit the gateway refuses
  every send with "402: insufficient credit". Messages you send are still
  written down and still go out after you top up - nothing is lost, it just
  waits. Only that state is coloured; a working gateway is a quiet grey line,
  so colour on this page always means something needs you.

  The balance is looked up at most once every 5 minutes. iprogSMS rate-
  limits that call, and being told "too many attempts" instead of a
  number would be worse than a number a few minutes old. A top-up therefore
  takes up to 5 minutes to show.

  Cost is roughly PHP 0.50-1 per message. Leak alerts are rare; budget well
  under PHP 100 a month for seven households.

SENDING ONE BY HAND
  Dashboard -> Notices & SMS
  1. Choose who it goes to:
       - Tick "All active households" for everyone. This is one click and is
         the common case - a scheduled interruption concerns the barangay.
       - Or type in the "Send to" box. It filters as you type, on the name or
         the household ID. Enter or a click adds them as a chip; the x on a
         chip removes them, and Backspace in an empty box removes the last.
     The chips stay visible while you write, so you can see who it is going
     to without reopening anything.
  2. Title and message
  3. Under "How to send it", tick "Show in the app", "Also send as SMS", or
     both. At least one is required. Send notice is on the same line.

  A counter shows how many texts it will cost. Over 160 characters it is
  split into numbered parts.

AUTOMATIC LEAK ALERTS
  When a line is flagged, TWO texts go out:

    To the household owner:
      LEAK ALERT HH-001: possible leak Sep 16 1:08PM, moderate. Please check
      all your faucets are closed. If they are and water still runs, tell the
      facilitator.

    To the facilitator:
      LEAK: HH-001 (Maria Santos), moderate. 0.20 bar, 1.40 L/min. Detected
      by night flow. The owner has been asked to check their faucets.

  They are worded differently on purpose. The owner is asked to check their
  own taps first - a small leak and a tap left slightly open are identical to
  the sensors, and the tap is far more common. The facilitator needs to know
  which house and how bad, to decide whether to go.

  Both fit in one message. An all-clear is sent in the app only.

  Switch either off in .env:
      SMS_AUTO_ON_LEAK=False
      SMS_FACILITATOR_ON_LEAK=False

  THE FACILITATOR NEEDS A CONTACT NUMBER or their copy is silently skipped.
  Set it in Django admin -> Users -> facilitator -> Contact number.

"RECENTLY SENT"
  Rows, not cards. Every reply you write in a complaint thread also becomes a
  notice for that owner, so this list is mostly one-line replies - seven
  short messages used to fill the whole panel, and it grew with every reply
  ever sent.

  A reply is shown as one compact line and LINKS TO THE THREAD, which is
  where you can actually do something about it. Several replies in a row to
  the same complaint are folded into one line with "+2 more replies".

  Notices you composed keep their title, in bold, with an envelope.

READING THE DELIVERY LOG
  Queued            not handed over yet. Normal for a few seconds.
  Sent to network   the gateway accepted it and is delivering it.
  Delivered         it reached the handset. This is confirmed, not assumed.
  Not delivered     the gateway tried and could not. Reason shown.
  Failed            could not be handed over at all after 3 attempts.

  "Sent to network" and "Delivered" are deliberately different. A gateway
  accepting a message is not a phone receiving it, and this table exists to
  answer one question: somebody says they never got a text - did one reach
  them?

  "Try again" re-queues anything that failed or was not delivered.

  A missing API key HOLDS messages without using up an attempt - that is a
  setup problem, not the message's fault.

PHONE NUMBERS
  09171234501, +639171234501 and 639171234501 are all accepted and converted.
  A number that is not a valid PH mobile is failed with that reason rather
  than being sent into nothing.

  THE HOUSEHOLD NUMBERS ARE STILL PLACEHOLDERS. HH-001 is +639171234567.
  Put a real number - yours - on one household and test with that before
  turning automatic alerts on, or the first real leak texts a stranger.

CHECKING IT FROM THE TERMINAL
      python manage.py send_sms              send now, and check delivery
      python manage.py send_sms --status-only  only check delivery
      python manage.py send_sms --watch        keep running

HOW THE CODE REACHES THEM

  1. Plug in the board, wait about a minute.
  2. On the phone, join WiFi "LeakDetect-Setup", password leakdetect123

  3. The setup page opens by itself; otherwise http://192.168.4.1/
  4. Choose the home WiFi, type its password, enter the setup code. Leave

     it worked. Settings > My device turns to CONNECTED within a minute.

THE STATUS CARD  (Settings > My device, updates every 5 s)
  No board fitted yet              nothing on the line - facilitator's job
  Board fitted, awaiting activation  the facilitator has not activated yet
  Ready to set up                  code shown; follow the steps
  Setup code expired               codes last 14 days; "Get a new setup code"
  Connecting...                    code accepted, waiting for first readings

                                   WiFi has no internet, or board unpowered.
                                   A new code can be requested.

                                   cut, WiFi down, or WiFi password changed
  The owner can re-send the current code or get a new one ONLY until the
  board has connected once. After that, a new code (which lets a blank
  board take over this identity) is the facilitator's call: Lines ->
  Devices -> Issue code.
  The facilitator is TEXTED when a board sends its first reading, and the

YOU NEVER TYPE THE API KEY. The board fetches it. A key is 43 mixed-case

WHEN A CODE DOES NOT WORK
  "could not reach the server"   The WiFi has no INTERNET, or the server is
                                 not running. WiFi alone is not enough.
  "already been used"            Codes work once. The owner gets a new one
                                 from Settings > My device (before the board
                                 has connected) or the facilitator from
                                 Dashboard -> Lines -> Devices.
  "has expired"                  Codes last 14 days. Same two places.

  Watch the serial monitor while it tries - it prints [CLAIM] lines.

REPLACING A DEAD BOARD
  Flash the spare with the same sketch, issue a new claim code for that
  household's board on the dashboard (Lines -> Devices -> Issue code), and
  enter it on the spare's setup page. The household keeps its history.

  It now forgets ONLY the network. The board's identity, the server address,
  the zero offsets and the thresholds are kept. Before this it wiped all of
  them, which is why zeroing appeared to be lost after a network change.

9f. BENCH TESTING WITHOUT THE VALVE OR THE GSM MODULE
============================================================================
The sketch has two switches at the top for hardware that has not arrived:

    #define VALVE_FITTED false
    #define GSM_FITTED   false

Leave both false until the hardware is actually wired. Set each to true when
it is, and re-flash.

WHY THIS MATTERS - IT IS NOT JUST TIDINESS
  With no valve and VALVE_FITTED true, the board would close nothing, then
  measure the pressure drift of an OPEN hose for five minutes and report it
  as a leak. Phantom leaks are worse than no leak detection: they teach
  everyone to ignore the alerts.

  With no module and GSM_FITTED true, every AT command waits out a timeout
  that never ends, inside a loop that is also serving the board's web page
  and uploading readings.

WHAT YOU GET WITH BOTH FALSE
  - Three of the four tests still run: burst, night flow, and sustained low
    flow. Only the sealed-line decay test is disabled, and it is the only one
    that needs the valve.
  - The dashboard shows the valve as "Not fitted" and hides the Test valve
    button by itself. No configuration needed on that side.
  - The board still boots faster - no 8-second valve travel, no 3-second GSM
    wait.
  - If the board ever cannot reach the server, the serial monitor prints
    "[GSM] No module - would have sent: ..." so you can still see that the
    fallback path was reached.
  - On boot it prints a line confirming what it thinks is wired:
        [HW] Valve NOT fitted (sealed-line test disabled), GSM NOT fitted.

YOUR LAPTOP AS THE SERVER
  That is the normal setup for now and needs nothing special:

    python manage.py runserver 0.0.0.0:8000

  The board finds the laptop by itself if the address changes (section 5),
  so a new IP does not mean touching the board. Leave the Server address
  field on the setup page alone.


============================================================================
9e. THE FOUR LEAK TESTS  (what the board actually does now)
============================================================================
There is no calibration any more. The K = Q/sqrt(P) method is gone, along
with the C / A / F commands. The board now judges by PATTERNS over time:

  1. BURST       Flow above 3 L/min AND pressure below half what this line
                 normally sits at, for a minute. Normal use does not crash
                 the pressure; a split hose does.

  2. NIGHT FLOW  Any flow for 5+ minutes between 1 AM and 4 AM. Needs the
                 clock, which comes from the internet - so this test is
                 silent until the board has been online once.

  3. SUSTAINED   0.2-2 L/min that never returns to zero for 30 minutes.
     LOW FLOW    Nobody runs a tap that low that long. A tap left slightly
                 open looks identical, which is why the alert asks the owner
                 to check their faucets first.

  4. VALVE TEST  After 10 minutes of no flow, the board closes the valve,
                 waits 30 s, then watches the pressure for 5 minutes. A
                 sealed line holds it; a hole bleeds it away. This is the
                 ONLY test that finds a pinhole. Runs about once an hour.
                 If anyone opens a tap during it, the valve reopens at once
                 and the test is abandoned.

  Low pressure with nothing flowing is LOW SUPPLY, not a leak.

THE VALVE
  It is opened on boot, before anything else, so a power cut can never leave
  a house with the water shut off. It is closed only during a test, for about
  4-6 minutes, and only when the line has been idle.

  Manual controls are on the board's own page: "Run valve test now" and
  "Open valve". Both need the config password.

  Serial: V = test now, O = open, N = pretend it is night (for testing).

12. OTHER PROBLEMS AND FIXES
============================================================================
"This site can't be reached" / ERR_CONNECTION_REFUSED
    The server is not listening on the network. Section 7, step 1.

Chrome forces https:// and the server log fills with "code 400, message Bad
request version" garbage
    Chrome is upgrading the address to HTTPS. The dev server only speaks
    HTTP. Type the address WITH "http://" in front. If it still happens:
    Chrome -> Settings -> Privacy and security -> Security ->
    turn OFF "Always use secure connections". An Incognito window is a
    quick test.

The page looks broken - giant icons, no layout
    The service worker served an old stylesheet. Press Ctrl+Shift+R.
    If it persists: F12 -> Application -> Service Workers -> Unregister,
    then reload. (The cache is now named after the file contents, so this
    should not recur.)

The C: drive is full / upload fails / compiler "out of memory"
    Clear the temp folder: press Win+R, type %TEMP%, Enter, Ctrl+A, Delete.
    Close the Arduino IDE first. Skip any file that is in use.
    For more space: Disk Cleanup -> "Clean up system files" ->
    Windows Update Cleanup.

Dashboard shows a leak on a line reading 0.00 L/min
    That is the valve test doing its job. It found the line losing pressure
    while sealed, which is a leak too small for the flow sensor to register -
    see section 9e. If the pressure reading also sits at its maximum, check
    the sensor wiring instead.

The board's page says "Not claimed"
    It has no identity yet. Enter a claim code on its setup page - section
    9d. Until then it does not upload at all, deliberately: an unclaimed
    board posting every 2 seconds would only collect 401s, and a 401 looks
    exactly like a wrong server address.

The server log shows "database is locked" and a POST /api/ingest/ 500
    That batch of readings was dropped because two things tried to write at
    the same moment. Fixed in the settings by switching the database to WAL
    mode, which lets reading and writing happen together.
    If it ever returns, the usual cause is the database file being on slow
    or failing storage - it lives on the USB drive. Copying the project to
    the internal drive would make it far less likely.

The map fills with yellow "Access blocked" tiles
    OpenStreetMap could not tell which app was asking and served a blocked
    image instead of the map. Fixed in the settings (SECURE_REFERRER_POLICY),
    but your browser will have cached the blocked images - press
    Ctrl+Shift+R once to clear them.
    If it ever comes back: the map is optional. Press "Switch to offline
    schematic" and carry on; the schematic needs no internet at all.

The device page shows the wrong upload result
    http://<device-ip>/status shows server_url and server_upload, which is
    the fastest way to see what the board is actually trying to do.

12b. HOUSEHOLDS, COORDINATES AND THE LEAK MAP
============================================================================
ADDING A HOUSEHOLD
  Dashboard -> Households -> "Add household". It opens a dialog.
  The Household ID is assigned automatically (HH-001, HH-002, ...) - you no
  longer type it. The dialog shows which one it will get.

EDITING A HOUSEHOLD
  Dashboard -> Households -> "Edit" on the row. It opens a dialog with the
  current details already filled in. The Household ID is fixed and is not
  editable.

DELETING A HOUSEHOLD
  Dashboard -> Households -> "Delete" on the row. A confirmation dialog
  lists exactly what goes with it before you commit:

      - that household's complaints
      - that household's notices
      - the owner's Owner Portal login

  All of it is permanent; there is no undo in the dashboard. Pressure
  readings and leak events are NOT affected, because those are recorded
  against the hose line rather than the household.

  If you only want to stop an owner using the system, set their Account
  status to Inactive with Edit instead of deleting them - that keeps the
  record and its history.

COORDINATES
  Latitude and longitude are optional. Fill them in and the household
  appears as a pin on the leak map. Leave BOTH blank if not yet surveyed -
  one without the other is rejected.

  Format: decimal degrees, e.g.  9.6620  and  125.5290
  Sison is roughly latitude 9.61 to 9.70, longitude 125.44 to 125.54.

  Anything outside the municipality is refused, because a mistyped digit
  puts the household hundreds of kilometres away and on the map it just
  looks like a pin in the sea rather than an obvious mistake.

  To get a coordinate: stand at the house, open Google Maps on your phone,
  long-press your location, and copy the two numbers it shows.

THE MAIN SOURCE (where every hose starts)
  Dashboard -> Lines -> the box at the top of the page.
  This is the single point every household's hose runs from. Give it a name
  ("Main source", "Spring box", "Reservoir tank"), its coordinates, and an
  optional note like "beside the barangay hall". Same coordinate rules as
  households.

  It used to be called the main valve, back when it was the 0 m mark that
  distance markers were measured from. There are no distance markers now,
  and the valves that matter are the motorised ones on each household's
  line - so calling this one a valve too would only confuse the two.

THE LEAK MAP
  It draws the real municipal boundary of Sison (dashed blue outline) from
  the official NAMRIA / PSA data, so the map is always framed on the right
  place even before anything has been surveyed.

  - The main source is a PURPLE square with a pulsing ring and a permanent
    "Main source" label. Purple is used for nothing else, so it is the
    easiest thing on the map to find.
  - Households with coordinates appear as round pins that carry TWO pieces
    of information at once:
        the FILL colour is that household's own hose colour
            one colour per household, shown in the legend under the map
        the RING colour says what state that line is in
            green = normal, amber = low supply / maintenance,
            red = possible leak, grey = offline
    So a household keeps its identity on the map even when every line
    happens to be in the same state.
  - Each household's hose is drawn as its OWN line, straight from the main
    source to that house, in that household's colour:

        [source] ---- HH-001
                 \--- HH-002
                  \-- HH-003
                   \- HH-004

    One hose per house. They are NOT chained through each other: nothing is
    shared, and a run visiting the houses in turn would draw plumbing that
    does not exist and suggest a leak upstream affects everyone below it.

    A hose with no board fitted is drawn DASHED - the pipe is there, nothing
    is watching it yet.

    A LEAKING hose gets a RED OUTLINE and widens into a halo, while keeping
    its own colour inside. The outline carries the alarm so both read at
    once: you can still see whose hose it is while the red says something is
    wrong with it. It appears within about two seconds of the device
    reporting, without reloading the page.

    The line shows WHICH house a hose serves, not the route the pipe
    physically takes in the ground.
  - The hoses appear as soon as the households have coordinates. Nothing
    needs to be maintained by hand: add a household or move a coordinate and
    the map redraws itself.
  - "Switch to offline schematic" draws the hose run as a diagram instead.
    That view needs no internet and is the safe choice on a weak signal.

  Map tiles come from the internet. With no connection the map goes blank
  and the schematic is the one to use.


THE DEVICE'S OWN PAGE
  http://<device-ip>/ shows, above the live readings:

      Network       which WiFi it joined, and how strong the signal is
      This device   its own IP address
      Sending to    the server address it is posting readings to
      Last upload   whether the most recent one worked, and if not, what
                    happened the last time it went looking for the server

  That is the fastest way to answer "why is the dashboard not updating" -
  it tells you in one screen whether the problem is the WiFi, the server
  address, or neither. It refreshes itself every 3 seconds.


FINDING THE DEVICE'S OWN ADDRESS
  The Device status box on the dashboard shows the ESP32's IP underneath
  "just now". Click it to open the board's own page. It updates by itself
  when the board moves to a different network.

  DO NOT CONFUSE THE TWO ADDRESSES:
      192.168.1.9:8000   your laptop - the dashboard, /admin/
      192.168.1.13       the ESP32 - its own page and /wifi settings
  The board serves on the normal web port, so no ":8000" on its address.
  Asking Django for /wifi just gives a 404, because that page lives on the
  board, not on the server.

  The IP is also in Dashboard -> Lines, in the Devices table ("Last IP"),
  and the Serial Monitor prints it at boot.

12c. ADDING A HOSE LINE
============================================================================
Dashboard -> Lines -> "Add hose line". It opens a dialog asking for:

    Name        e.g. "HH-007 - Juan Cruz"
    Map colour  pick one of eight swatches

The line is created with NO device. A hose is laid long before a board is
fitted to it; attach the board later from Edit once it exists.

The colour is what that household's hose and pin are drawn in on the leak
map, so each house stays identifiable even when every line is in the same
state. You can change it later with Edit. The next unused colour is
pre-selected so two new lines never come out looking alike.

EDITING A LINE
  "Edit" on the row opens a dialog with the current values filled in -
  name, the device fitted to this line, map colour, the low-supply
  threshold, optional coordinates, maintenance note and whether the line is
  active.

DELETING A LINE
  "Delete" on the row asks for confirmation first and names exactly what
  goes: that line's minutes of pressure history and its leak events. Both
  are permanent.

  Households on the line are NOT deleted. They become Unassigned and stop
  receiving alerts until you move them to another line.

  If a sensor is only being repaired, use Maintenance instead of Delete -
  it silences that line's alerts and keeps every reading.

IMPORTANT - ADDING A LINE DOES NOT ADD A BOARD.
A new line shows "No device" until a board is fitted and claimed. That is
not a fault; it is the rollout working, and the dashboard keeps it visually
distinct from a board that has stopped reporting.

To make it live: register a board for it (Dashboard -> Lines -> Devices, or
tick "Register a new board" while adding the household), then claim that
board with its code - section 9d.

There is no line limit any more. One board serves one household, so another
household means another board, not another module on an existing one.

12e. SHOWING THE SYSTEM ON A PHONE WITHOUT DEPLOYING IT
============================================================================

IF THE PHONE IS ON THE SAME WIFI - nothing special needed
  1. Start the server with  python manage.py runserver 0.0.0.0:8000
     (the 0.0.0.0 matters; plain runserver is reachable only by the laptop)
  2. Open the "On the network" address it prints, on the phone.
  Works for anyone in the room, no accounts, no setup.

  IF THE PHONE SAYS "This site can't provide a secure connection"
  (ERR_SSL_PROTOCOL_ERROR), and the server window fills with lines like
  code 400, message Bad request version ('...'):

    The browser used https:// and this server only speaks http://. Those
    two lines are the same event - the phone sent an encrypted handshake,
    the server tried to read it as plain text. Nothing is broken.

    Type the address with http:// spelled out:

        http://192.168.1.3:8000/        <- your IP will differ

    If the browser keeps switching it back to https, it is forcing the
    upgrade and has to be told not to:
      Chrome / Edge: Settings -> Privacy and security -> Security ->
                     turn off "Always use secure connections"
      Or the phone is autocompleting an https address you used before -
      delete that suggestion rather than tapping it.

    Do NOT try to fix this on the server. Nothing in this project redirects
    to https, and there is no setting that stops a browser choosing it.

IF THE PHONE IS ON MOBILE DATA OR A DIFFERENT NETWORK
  1. Leave the server running.
  2. In VS Code: PORTS tab -> Forward a Port -> type 8000 -> Enter
  3. Sign in with GitHub when asked.
  4. Right-click the new row -> Port Visibility -> Public.
     Skip this and visitors hit a Microsoft login instead of your system.
  5. Copy the Forwarded Address (looks like
     https://xxxxx-8000.asse.devtunnels.ms) and open it on the phone.

  The URL changes every time you forward the port again. Django is already
  set up to accept it whichever address it gets, so there is nothing to edit.

  Leave the ESP32 pointed at the LAN address, not the tunnel. The board
  speaks plain HTTP and finds the server by broadcasting on the local
  network; neither of those crosses the internet. Board on the LAN, viewers
  on the tunnel - both work at the same time.

  Close the port (the X on the row) when you are done. While it is Public
  the login page is on the open internet.


SHOWING IT TO SOMEBODY FAR AWAY - USE CLOUDFLARE  (recommended)
  This is the one that works on this laptop. No account, no signup, no
  warning page for the visitor, and real HTTPS - so the portal can be
  installed and notifications switched on from it.

  ONE-TIME:   winget install --id Cloudflare.cloudflared

  EVERY SESSION, in a second terminal next to the running server:

      cloudflared tunnel --url http://127.0.0.1:8000

  It prints a https://....trycloudflare.com address. Send that to whoever
  needs it. Measured on 2 Oct 2026: 10 of 10 requests succeeded, the login
  page in 0.5 s and the 100 KB stylesheet in 1.3 s, over a Singapore edge.

  Use 127.0.0.1, not localhost - on this laptop "localhost" resolves to the
  IPv6 address ::1 first and the server only listens on IPv4.

  The address changes every time cloudflared restarts. Nothing needs
  editing: settings.py already trusts *.trycloudflare.com for CSRF.

  The laptop has to stay awake with both the server and cloudflared running.
  Closing either closes the door. For something that outlives the laptop,
  deploy the system properly instead of tunnelling.

WHY NOT THE OTHER TWO
  VS CODE PORT FORWARDING delivered static files but silently dropped every
  HTML page - app.css arrived, /login/ never did, while both answered
  instantly on 127.0.0.1.

  ngrok was worse on this machine: its agent endpoints are blocked here.
  ngrok.com loads fine, but connect.ngrok-agent.com and tunnel.us.ngrok.com
  cannot be reached at all and tunnel.ap.ngrok.com is cut during the TLS
  handshake, so the agent loops on "reconnecting" and the edge reports
  ERR_NGROK_3200 (endpoint offline). With region: ap set in ngrok.yml it
  improved to about 3 requests in 10 succeeding. Malwarebytes is installed
  on this laptop and blocks ngrok's agent domains by default - malware
  abuses ngrok, so it is on their block list. Cloudflare is not blocked.

  Keeping the ngrok notes below in case that block is ever lifted.

IF VS CODE'S PORT FORWARDING WILL NOT WORK - USE ngrok INSTEAD
  On 2 Oct 2026 the VS Code tunnel started delivering static files but
  silently dropping every HTML page: app.css arrived, /login/ never did.
  Nothing was wrong with the server - the same URLs answered instantly on
  127.0.0.1 and on the LAN. Rather than keep fighting it, use ngrok.

  ONE-TIME SETUP (already done on this laptop)
    winget install --id Ngrok.Ngrok
    ngrok update                      <- winget ships an old build that the
                                         service now refuses (ERR_NGROK_121)
    ngrok config add-authtoken <your token from dashboard.ngrok.com>

  EVERY SESSION
    1. Start Django as usual:   python manage.py runserver 0.0.0.0:8000
    2. In a SECOND terminal:    ngrok http 127.0.0.1:8000

       Use 127.0.0.1, not localhost. On this laptop "localhost" resolves to
       the IPv6 address ::1 first, and the server only listens on IPv4.

    3. ngrok prints a "Forwarding" line. Open that https:// address on the
       phone.
    4. The first visit shows an ngrok warning page ("You are about to
       visit..."). Tap "Visit Site". It appears once per device.

  THE ADDRESS CHANGES EVERY TIME ngrok RESTARTS on the free plan. Nothing
  needs editing when it does - settings.py trusts the ngrok wildcards for
  CSRF already, including the newer .ngrok-free.dev domain.

  Closing the ngrok terminal closes the tunnel. While it is open, the login
  page is on the open internet.

  Leave the ESP32 on the LAN address, exactly as with the VS Code tunnel.

  http://127.0.0.1:4040 is ngrok's own inspector - every request and
  response, which is the quickest way to see whether a phone reached you.

12f. INSTALLING THE PORTAL ON A HOUSEHOLD'S PHONE  (and turning on alerts)
============================================================================

WHAT THIS IS
  The Owner Portal is a Progressive Web App - a PWA. It is the website, but
  a phone can keep it on its home screen and open it full screen with no
  browser bar, like an installed app. There is no Play Store or App Store
  entry and nothing to download; the phone saves the page it already has.

  Owners find it at Portal -> Settings, which has the steps for their own
  phone and a button to turn on alerts.

  Careful with the letters: PWA is the app thing. WPA is the WiFi password
  thing. They are unrelated and the system uses both.

THE ONE REQUIREMENT - AN https:// ADDRESS
  No phone will install from http://192.168.x.x, and the alerts cannot be
  switched on there either. This is the browser's rule, not ours, and there
  is no way around it.

  Three addresses behave differently:

    http://127.0.0.1:8000       installs fine. Browsers trust localhost.
                                Only the laptop itself can open it.
    http://192.168.x.x:8000     does NOT install. This is the address phones
                                on your WiFi use (section 12e), so an owner
                                on the barangay WiFi cannot install from it.
    the VS Code forwarded URL   installs fine - it is https. Section 12e.
    a real hosted domain        installs fine, and is the only one that
                                survives the laptop being closed.

  The Settings page says so itself: on an address that will not work it
  shows an amber note instead of pretending the button will do something.

ON AN ANDROID PHONE
  1. Open the portal in Chrome and sign in.
  2. Go to Settings in the menu.
  3. Tap "Install on this phone".
     (If that button is not there: three dots at the top right ->
      "Install app" or "Add to Home screen".)

ON AN iPHONE OR iPAD
  There is no install button on an iPhone. Apple does not give web pages
  one, so it is always done by hand:

  1. Open the portal in SAFARI. Chrome on an iPhone cannot install it.
  2. Tap Share - the square with the arrow pointing up, at the bottom.
  3. Scroll down, tap "Add to Home Screen", then "Add".

TURNING ON ALERTS
  Portal -> Settings -> "Turn on alerts". The phone asks for permission
  once; after that a leak on that household's line puts a notification on
  the screen even with the app closed. "Send a test" proves it end to end.

  On an iPhone the app MUST be installed to the home screen first. Apple
  does not deliver notifications to a web page in Safari - only to an
  installed one, on iOS 16.4 or newer.

  Alerts never replace the SMS. The text goes out regardless, to every
  household with a number on file. Notifications are a second, faster route
  for the phones that have asked for them, and a phone that is off, out of
  battery or out of signal simply does not get one.

SETTING IT UP ON THE SERVER  (once, by the facilitator)
  Nothing is registered with Google, Apple or anybody else. The server
  signs its own notifications with a key pair it generates:

      python manage.py make_push_keys

  It prints three lines. Paste them into .env and restart:

      VAPID_PUBLIC_KEY=...
      VAPID_PRIVATE_KEY=...
      VAPID_SUBJECT=mailto:your-email@example.com

  Generate these ONCE. Every phone's subscription is tied to the public key
  it saw when it was set up, so making a new pair silently stops
  notifications on every phone that already has them, with no error
  anywhere - each household would have to turn them on again.

  Until the keys exist, Settings tells the owner plainly that notifications
  are not set up yet and that nothing is wrong with their phone.

WHEN A HOUSEHOLD SAYS THEY GET NOTHING
  - Did they install it? On iPhone, nothing arrives until it is on the home
    screen.
  - Is the address https? Check what link they were given.
  - Is their phone's notification permission still allowed? If they tapped
    "Block" once, the browser will not ask again - it has to be changed in
    the phone's settings for that site.
  - Did they turn alerts off, or clear their browser data? Both unregister
    the phone. Settings -> Turn on alerts again.
  - Is PUSH_ENABLED=false in .env?

  The SMS log (section 9c) is the independent record. If the text went and
  the notification did not, the problem is on the phone, not the server.

12g. WHEN SOMEBODY LANDS ON A PAGE THAT ISN'T THERE
============================================================================

  A mistyped address, an old bookmark or a stale link now gets a proper page
  saying so, with the address it tried and links to wherever that person
  belongs - the dashboard for you, the portal for a household, the sign-in
  page for anyone else. There are four:

      404  the page does not exist
      403  the account cannot open that page (facilitator pages and
           household pages are separate; this says so rather than looking
           like a fault)
      400  the request was malformed - usually a form left open so long its
           security token expired
      500  something broke on the server

  YOU WILL NOT SEE THEM WHILE DEVELOPING
  With DEBUG=True Django shows its own yellow traceback page instead, no
  matter what templates exist. That is deliberate on Django's part and
  nothing is wrong. To look at the real pages:

      set DEBUG=False in .env, restart, and visit any wrong address
      (runserver also needs --insecure to keep serving CSS with DEBUG off)

  Put DEBUG back to True afterwards, or you lose the traceback that tells
  you what actually went wrong while you are building.

  WHY DEBUG MUST BE False WHEN THIS IS HOSTED
  The traceback page lists every URL pattern in the project to whoever
  typed the bad address - including api/claim/ and the device key endpoints.
  It also prints settings and local variables on a crash. It is a
  development tool and it must never be reachable from the internet.

  The 500 page is deliberately plain and does not use the site's stylesheet
  or layout. If the thing that broke is the database or the static files, a
  nicely styled error page would fail for the same reason and the visitor
  would get Django's bare "A server error occurred" instead. It also tells
  the household the one thing worth knowing: detection runs on the board at
  their house, so their line is still being watched while the website is
  down.

15. SCALING  (this is now how the system works)
============================================================================
Superseded 16 Sep 2026. The plan here used to be "one ESP32 per zone, three
lines each", written while the rig was three sensor pairs sharing a board. It
was never built, and the design moved past it.

HOW IT WORKS NOW
  One board serves one household. Adding a household means adding a board,
  and no existing board is opened, re-flashed or disturbed.

  There is no line limit. The old ceiling of about five lines per board came
  from running out of pins: pressure sensors need ADC1 pins (32-39), because
  ADC2 stops working while WiFi is on, and flow sensors need interrupt-
  capable pins, which rules out 34-39. One sensor pair per board removes that
  constraint entirely.

  Boards are numbered separately from households - esp32-01, esp32-02 - and
  the server links a board to a household's line. A board is a physical
  object with a service life; a household is a place. Naming the board after
  the house would mean a replacement board had to reuse that name, and the
  event log could then never tell the original board from the one fitted
  after it failed.

WHAT IT COSTS PER HOUSEHOLD
  An ESP32, a pressure sensor, a flow sensor, a motorised ball valve (about
  PHP 938), a 2-channel relay, and the fittings. The valve is the largest
  single item - see section 14.

THE ONE THING THAT DOES NOT SCALE YET
  The server. It is one machine running `runserver`, which is a development
  server and says so. Past a handful of boards posting every 2 seconds it
  should move to a real WSGI server, and the readings table will need
  trimming - a minute-level rollup already exists, but the raw table grows
  without bound.

16. DEPLOYING TO PYTHONANYWHERE
============================================================================

  What deploys cleanly: the whole web side - dashboards, the owner portal,
  the landing page, complaints, logins. What does NOT work on the free tier,
  and why, is at the bottom of this section. Read that before you promise
  anybody a live text message.

  BEFORE YOU START
    - Push your commits to GitHub. PythonAnywhere pulls the code from there.
    - Pick Python 3.13 when it asks (3.11 or 3.12 are fine too). This laptop
      runs 3.14, which PythonAnywhere does not offer yet; Django 5.2 is happy
      on any of these.

  ONE-TIME SETUP
    1. On pythonanywhere.com, open a Bash console and clone the repo:
           git clone https://github.com/<you>/SmartHoseLeak.git
           cd SmartHoseLeak

    2. Make a virtualenv and install:
           mkvirtualenv shl --python=python3.13
           pip install -r requirements.txt

    3. Create the .env file (it is gitignored, so it is not in the clone):
           nano .env
       Put in at least these four lines:
           DEBUG=False
           SECRET_KEY=<paste a fresh key - see below>
           ALLOWED_HOSTS=<you>.pythonanywhere.com
           CSRF_TRUSTED_ORIGINS=

       Generate the key in the same console:
           python -c "from django.core.management.utils import get_random_secret_key as g; print(g())"

       CSRF_TRUSTED_ORIGINS can stay blank - the server derives
       https://<you>.pythonanywhere.com from ALLOWED_HOSTS by itself.

       The server WILL REFUSE TO START if DEBUG=False and either SECRET_KEY is
       still the development default or ALLOWED_HOSTS is empty. That is on
       purpose - it tells you exactly what is missing in the error log rather
       than running insecure.

    4. Set up the database and static files:
           python manage.py migrate
           python manage.py collectstatic --noinput
           python manage.py createsuperuser

    5. In the PythonAnywhere "Web" tab:
         - Add a new web app, "Manual configuration", Python 3.13.
         - Source code:   /home/<you>/SmartHoseLeak
         - Virtualenv:    /home/<you>/.virtualenvs/shl
         - Edit the WSGI file it generates: set
               os.environ['DJANGO_SETTINGS_MODULE'] = 'config.settings'
           and point it at the project (the stock Django block, pointing at
           config.wsgi, works as-is).
         - Static files mapping:
               URL:  /static/        Directory: /home/<you>/SmartHoseLeak/staticfiles
         - Click "Reload".

    6. Confirm it is set up right. In the console:
           python manage.py check --deploy
       Two warnings are expected and fine: SECURE_SSL_REDIRECT and
       SECURE_HSTS_SECONDS are off by default. Turn them on in .env once you
       have confirmed HTTPS works end to end (SECURE_SSL_REDIRECT=True, then
       SECURE_HSTS_SECONDS=2592000) and reload.

  UPDATING AFTER A CODE CHANGE
      git pull
      pip install -r requirements.txt          # only if requirements changed
      python manage.py migrate                 # only if there are new migrations
      python manage.py collectstatic --noinput
      # then hit "Reload" in the Web tab

  WHAT DOES NOT WORK ON THE FREE TIER
    SMS and push notifications both reach OUT to the internet (Semaphore's
    gateway; the browsers' push services). The free tier only allows outbound
    traffic to a fixed allowlist of sites, and those are not on it - so both
    silently fail there. They need a PAID tier, which has open outbound.

    SMS also needs a worker. The queue is drained by a background thread that
    only runs under "runserver" - under the hosted WSGI it never starts. On a
    paid account, add an Always-on task running:
        python manage.py send_sms --watch
    (or a Scheduled task running "python manage.py send_sms" on the shortest
    interval your plan allows). The free tier's once-a-day task is far too
    slow for a leak alert.

    The ESP32 cannot be found over the internet: it discovers the server by
    UDP broadcast on the LAN and would have to be pointed by hand at
    https://<you>.pythonanywhere.com/api/ingest/ instead. For a defence it is
    simpler to demonstrate the hosted site with the data already in it, and
    show the live board separately against a laptop server over a tunnel
    (section 12e).

    In short: the free tier is enough to put the whole interface online for a
    panel to click through. Live SMS, live push and a live board over the
    internet are a paid tier plus the worker task above.
